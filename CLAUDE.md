# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A Databricks AI Runtime (AIR) demo for DAIS: fine-tune `Qwen/Qwen3.5-4B` with Hugging Face TRL supervised fine-tuning + PEFT LoRA on IBM TabFormer credit-card fraud transactions, register the merged model to Unity Catalog as a custom LLM, deploy it to Mosaic AI Model Serving (vLLM), and load test the endpoint at high QPS. The deliverables are Databricks notebooks plus YAML configs and the CLI training image in `train/docker/` (Dockerfile plus push script) — there is no test suite or linter, and the only build step is that image.

## Databricks Notebook Source Format

Every `.py` file in `setup/`, `train/`, and `load_test/` is a Databricks notebook **except `train/train.py`**, which is a plain Python module holding the training implementation (imported by the training notebook and executed directly by the AI Runtime CLI per `train/train.yaml`). When editing notebooks, preserve the format: `# Databricks notebook source` header, `# COMMAND ----------` cell separators, `# MAGIC %md` markdown cells.

- Every consumer (the three notebooks, `train.py`, local scripts) gets the shared helpers (`load_yaml_config`, `config_str`/`config_int`/`config_float`/`config_bool`, `quote_identifier`, `full_name`, `get_spark_session`, `load_training_config`, `init_training_workspace`) the same way: insert the `train/` directory into `sys.path`, then `from training_utils import ...`. Never `%run` it, and never add the `# Databricks notebook source` header to it — notebook-formatted files cannot be imported in the workspace (`NotebookImportException: Importing notebooks directly is not supported`), and `train.py` must be able to import the module under the runner notebook, the AIR CLI, and local runs alike.
- The helpers module must **never** be renamed back to `utils.py`: the Databricks AI GPU base environment's `nvidia_cutlass_dsl` package registers a top-level `utils` module once torch/CUDA loads (e.g. when `train.py` imports `trl`, which pulls in transformers and torch), poisoning `sys.modules` so a local `from utils import ...` resolves to cutlass's vendored module and fails with `ImportError: cannot import name ... from 'utils' (...nvidia_cutlass_dsl/...)`.
- Training config flows through `training_utils.load_training_config()`, which returns a flat dict that the runner notebook and `train.py` each bind with `globals().update(...)` — so both see identical constants (`MODEL_NAME`, `TRAINING_OUTPUT_DIR`, `sft_table_q`, ...). It reads `parameters.training_config` from the YAML file at `$HYPERPARAMETERS_PATH` when AIR sets it (so `databricks air run --override` values reach the script), falling back to `train.yaml` next to `training_utils.py`. `databricks air run` writes only the `parameters` mapping to that file (`hyperparameters.yaml`, with override values YAML-typed), so `experiment_name` and `mlflow_experiment_directory` are read from the snapshot's `train.yaml`; the full-workload shape the deprecated Python CLI wrote is still accepted. It is deliberately a function, not top-level module code, so importing `training_utils` has no side effects (no config parse, no Spark, no schema creation). `load_yaml_config` resolves paths against the module's own directory by default; callers in other folders (the load-test notebook) pass `base_dir=Path.cwd()` for their own YAML.
- Notebooks support dual execution: inside Databricks (serverless notebooks, where `Path.cwd()` is the notebook's folder) or locally via Databricks Connect. `get_spark_session()` in `training_utils.py` attaches a serverless Connect session when none exists; `setup/01_load_tabformer_dataset.py` resolves its own directory via `__file__` with a `dbutils` notebook-context fallback before importing the helpers from `train/`.
- Notebook installs use `%uv pip` (followed by `%restart_python`), not `%pip`. It shares the notebook virtualenv with `%pip` but needs a **serverless notebook on environment version 5+** — classic compute and older serverless versions don't support it — and it does not check new installs for conflicts against already-installed packages (which is why the serving stack's deliberate opencv downgrade is silent). Quote requirement specifiers that contain `>`/`<`.

## Architecture: Three-Stage Pipeline Coupled by YAML Configs

Each stage is a notebook driven by a sibling YAML file, connected to the next stage only through Unity Catalog objects:

1. **Ingest** — `setup/01_load_tabformer_dataset.py` + `setup/setup.yaml`: downloads TabFormer into a UC staging volume, writes the cleaned transaction table (`fraud_dataset`) and the SFT table (`fraud_sft_dataset`) with `prompt`, `assistant_response`, and `shard_id` columns, then exports the SFT records to the `training_data` volume as Parquet partitioned by `shard_id` (the AIR data-loading pattern for large Delta tables). **Overwrites the tables and the export on every run.** Creates the schema and volumes if missing.
   `setup/02_load_model_weights_to_volume.py` (same `setup.yaml`) is an optional adjunct to this stage: it mirrors the `model_name` checkpoint from the Hugging Face Hub into the `model_volume` volume, one file at a time (download to local disk → stream to the volume → delete the local copy), so local disk stays bounded and volume writes stay sequential (parallel large safetensors writes to volume FUSE hit EAGAIN). It resolves `model_revision` to a commit SHA and fetches every file at that SHA, skips files already present at the Hub-reported size unless `force_model_download`, writes provenance to `<model>_download_metadata.json` **beside** (not inside) the weights directory so the mirror stays a byte-for-byte Hub snapshot, and verifies config/tokenizer/index-shard completeness. Nothing consumes it automatically — point training at it by setting `train.yaml`'s `model_name` to the `/Volumes/...` path.
2. **Train / register / deploy** — `train/runner.py` + `train/train.yaml` (one file: top-level AIR CLI workload schema with the demo's own configuration nested under `parameters.training_config`, the schema's designated field for custom structured config — `databricks air run` decodes the YAML strictly and rejects unknown keys at any level). `train.yaml` is laid out for the demo in three commented sections: the AIR fields the CLI **requires** (`experiment_name`, `compute`, `command`) together at the top, then the optional workload fields (`environment`, `code_source`, `mlflow_experiment_directory`, `max_retries`), then `parameters` — keep new workload fields in the matching section: reads the SFT table, fine-tunes with TRL `SFTTrainer` + PEFT LoRA, saves rank-0 adapters to a UC volume, then (in later cells) merges the adapter, registers to UC, and creates/updates the serving endpoint. The training implementation is `train/train.py` (`run_rank_training()` trains one rank's shard slice; rank/world size are resolved launcher-agnostically); the notebook's `@distributed(gpus=N, gpu_type="h100")` cell is a thin wrapper that inserts `NOTEBOOK_DIR` into `sys.path` on each worker and calls it, and the AI Runtime CLI runs the same file standalone (`databricks air run --file train/train.yaml`, which launches it under `torchrun --standalone`; multi-node would need the documented `NUM_NODES`/`NODE_RANK`/`LOCAL_WORLD_SIZE`/`MASTER_ADDR`/`MASTER_PORT` rendezvous form noted in `train.yaml`). The registration cell imports `load_adapter_model` from the same module (`AutoPeftModelForCausalLM` + tokenizer, which it then `merge_and_unload()`s). Creates the schema and the checkpoint volume if they don't exist (the SFT table itself still comes from setup).
3. **Load test** — `load_test/load_test_serving_endpoint.py` + `load_test/serving_load_test.yaml`: samples prompts from the SFT table, smoke-tests the endpoint, then generates paced async HTTP traffic from Spark tasks via `mapInPandas` + `aiohttp`. **Appends** a summary row to the results Delta table.

### Cross-file contracts (keep these in sync)

- **Config coupling**: `catalog`, `schema`, and `sft_table` must agree across all three YAML files (the training values sit under `train.yaml`'s `parameters.training_config` key); `endpoint_name` must match between `train.yaml` and `serving_load_test.yaml`; `serving_load_test.yaml`'s `enforce_json_schema` toggles the `response_format` grammar constraint (the schema itself lives in `training_utils.FRAUD_RESPONSE_JSON_SCHEMA`, shared by the load test and the notebook's sample payloads); `setup.yaml`'s `table` must equal `train.yaml`'s `source_table`; `setup.yaml`'s `model_name` must equal `train.yaml`'s `model_name` unless `train.yaml` has been repointed at the mirrored `/Volumes/...` path (the mirror is only useful if it holds the checkpoint training loads); `sft_volume` must match between `setup.yaml` and `train.yaml` (it locates the Parquet export training reads). `train.yaml`'s top-level `experiment_name` + `mlflow_experiment_directory` are the only place the MLflow experiment is named and located — AIR creates the experiment at `<directory>/<experiment_name>` (the user's home when the directory is unset), and the runner notebook resolves the same two fields to the same path via `training_utils.resolve_experiment_path()`. The name must stay alphanumeric/`-`/`_` and ≤100 characters (the CLI validates this, since it becomes the Jobs API task key); the directory must start with `/Workspace/`. `train.yaml`'s `environment.unity_catalog_image` must name the image pushed from `train/Dockerfile` (`train/docker/build_and_push.sh` reads that field as its push destination, so the image name and tag change only there), and `train/requirements.txt` is the single training dependency list for both launchers — after editing it, rebuild and push the image (bump the tag) or CLI runs keep the old stack.
- **Shard contract**: ingestion computes `shard_id` as `pmod(xxhash64(...), sft_shards)` (128 shards) and exports the SFT records as Parquet partitioned by `shard_id` into `/Volumes/<catalog>/<schema>/<sft_volume>/<sft_table>/shard_id=N/`. `run_rank_training()` claims the directories where `N % world_size == rank` and loads them with Hugging Face `datasets` (`load_dataset("parquet", ...)`) — no Spark session on the GPU workers. Sampling is two-level: for `sample_fraction < 1` only a seeded-random subset of the rank's shard directories is loaded (hash shards are uniform, so this is equivalent to row sampling) and row-level sampling within the loaded shards lands on the exact fraction — this keeps the HF `datasets` Arrow conversion ("Generating train split") proportional to the fraction instead of always materializing the full slice, per https://docs.databricks.com/aws/en/machine-learning/ai-runtime/dataloading#load-large-delta-tables-using-unity-catalog-volumes. Parquet was chosen because training consumes HF `datasets`, which memory-maps Parquet natively.
- **Prompt contract**: the prompt text is built once in ingestion (Spark `concat` expressions) and the assistant response is compact JSON with keys `risk`/`action`/`reason`. Training, the sample serving payload, and the load test all reuse this exact shape; if you change the prompt template in setup, the sample payload in the training notebook must match. The contract also includes **thinking suppression, enforced in two independent layers** because a request that loses it produces a reasoning preamble instead of JSON. (1) *Server-side default*: `train.py` renders training data with `CHAT_TEMPLATE_KWARGS = {"enable_thinking": False}`, and the merge step rewrites the served checkpoint's `chat_template.jinja` so the same render is the **default** — upstream Qwen3.5 emits a bare `<think>\n` unless told otherwise, and `default_thinking_off()` inverts that to emit the closed `<think>\n\n</think>\n\n` unless a request opts in with `enable_thinking=true`. This is what makes the AI Playground and plain `curl` behave. (2) *Grammar constraint*: requests may also send `response_format` built from `training_utils.fraud_response_format()`, which admits only tokens fitting the `risk`/`action`/`reason` schema, so no preamble is representable at all (verified against the live endpoint: schema alone, with the kwarg omitted, still returned valid contract JSON). The schema's enums must stay in step with ingestion's `risk_col`/`action_col`. **Placement trap**: `chat_template_kwargs` must sit at the **top level** of the request body. Nesting it under `extra_body` is silently ignored by vLLM — `extra_body` is a client-side-only concept that the OpenAI SDK flattens before sending, so it works from the SDK and fails from raw JSON/curl. Layer 2 guarantees the response *shape*, not its *quality*: with the kwarg lost, the model answers from a prompt state the fine-tune never saw and can emit a well-formed but internally inconsistent decision, so keep both layers rather than relying on the schema alone.
- **Serving contract**: registration wraps merged HF weights in an MLflow pyfunc whose `metadata` carries `task: llm/v1/chat` and a vLLM OpenAI-server `entrypoint` listening on port 8080 (the port Model Serving expects), with `--language-model-only` so only Qwen3.5's text backbone is served. **The logged weights must be in the base model's composite (vision + text) shape**, not the text-only shape training produces — see the vLLM architecture-registry bullet below. The entrypoint launches from the model's `artifacts/` folder, so the `--model` path must be the bare artifact name — an `artifacts/` prefix makes vLLM treat it as a Hugging Face repo id and fail with a 401. Entrypoint models must be registered with `env_pack="databricks_model_serving"` (express deployment), which needs `databricks-sdk>=0.102.0` to avoid a 5-minute timeout uploading the env-pack tarball. The pyfunc placeholder class is deliberately defined inline in the registration cell so cloudpickle serializes it by value — no `code_paths` are logged, and none are needed as long as the logged model imports nothing from the repo (the vLLM entrypoint, not the pyfunc, serves traffic). The serving container's environment is **not** declared in `pip_requirements`: it is installed in the notebook in two `%uv pip` passes (`vllm==0.24.0` + `transformers==5.13.0` + `mlflow==3.14.0` + `flashinfer-cubin`, then `opencv-python-headless==4.12.0.88` on top) and captured by `env_pack`. `log_model` passes only `extra_pip_requirements=["mlflow==3.14.0"]`. A single requirements list is resolved in one pass and cannot hold both vLLM's `opencv>=4.13` floor and the FIPS-safe 4.12 pin — see the opencv/FIPS bullet below. Both sides now run transformers 5, so the old training-5/serving-4 straddle is gone. vLLM settings (`vllm_dtype`, `vllm_max_model_len`, `vllm_gpu_memory_utilization`) come from `train.yaml`'s `parameters.training_config`.

### Ordering dependencies inside the training notebook

Registration is now **three cells**, because the training and serving environments cannot share one Python session:

1. **Merge** — needs `TRAINED_ADAPTER_OUTPUT_DIR`/`TRAINING_RUN_ID` from the training cell. Loads the rank-0 adapter, `merge_and_unload()`s it, and writes plain HF weights to `/local_disk0/air-demo-merged/<artifact>` (local disk, not `/Volumes`: it survives the restart below and avoids the EAGAIN failures large safetensors writes hit on the volume FUSE mount). It also rewrites the saved `chat_template.jinja` so thinking is off by default (see the prompt contract), then writes `merge_metadata.json` next to the weights.
2. **Install the serving stack** — two `%uv pip` passes (vLLM first, `opencv-python-headless==4.12.0.88` second) followed by `%restart_python`.
3. **Register** — the restart wipes all session state, so this cell re-inserts `sys.path`, re-runs `load_training_config()`, re-sets the MLflow experiment, and reads `merge_metadata.json` for the adapter dir, training run id, and merged-weights path. **State crosses the restart boundary through that file, never through Python globals** — if you add anything the registration cell needs, put it in the JSON.

The deployment cell requires `REGISTERED_MODEL_VERSION` from registration (`register_model`/`deploy_endpoint` flags in `train.yaml`'s `parameters.training_config` gate these). Registration is deliberately separate from training so a failed registration or deployment can be rerun without re-training. Scaling is done by editing only the `gpus=` value in the `@distributed` decorator on the single training cell. The dataset sampling fraction is config-driven for both launchers: `load_training_config()` binds `train.yaml`'s `training_sample_fraction` as `TRAINING_SAMPLE_FRACTION`, and the training cell forwards it into `run_rank_training(sample_fraction=...)` — change the YAML (or `databricks air run --override parameters.training_config.training_sample_fraction=...`) rather than reintroducing a hardcoded value in the cell.

### Other constraints

- The two launchers run the **same dependency list in different environments**. The runner notebook uses the **Databricks AI environment, serverless GPU version 6** (Public Preview; `AI v6` in the notebook compute picker): Python 3.12, CUDA 13, torch 2.11.0+cu130, transformers 5.8, trl 0.24, peft 0.19, accelerate 1.13, datasets 4.8, flash-attn 2.8/3.0, with `requirements.txt` installed on top. CLI runs use the custom image built from `train/Dockerfile` (next bullet), which installs the same `requirements.txt`. Declarative bundles select the AI environment with `base_environment: databricks_ai_v6`; in a workload YAML it is `environment.version: databricks_ai_v6` — a bare numeric `6` selects the **Standard** environment, which ships no torch, transformers, or trl. The AI v6 environment **removed `bitsandbytes`, `xformers`, and `unsloth`** — hence `optim="adamw_torch_fused"` instead of the old `adamw_8bit` (which needed bitsandbytes; with LoRA the optimizer state is negligible either way). The `torch==2.11.0` pin in `requirements.txt` matches AI v6's bundled CUDA 13 build (a no-op there) and stops any other requirement from swapping it out.
- **CLI training image** (`train/docker/`, Beta feature). `train/docker/Dockerfile` is `FROM databricksruntime/air:dcs-base-aws-runtime-cu13` — Databricks' AWS base image with CUDA 13.0.3, NCCL 2.28 + EFA/aws-ofi-nccl, Python 3.12 in a uv venv at `/opt/venv` (on `PATH`), and `OPENSSL_FORCE_FIPS_MODE=0` preset for AI Runtime's FIPS hosts, but **no ML libraries**. It installs `train/requirements.txt` from a single package index — the `PYPI_INDEX_URL` build arg, default public PyPI — then asserts `torch.version.cuda` is 13.x so a wrong wheel fails the build instead of a GPU run. No PyTorch index is needed: PyPI's torch 2.11.0 Linux wheel already is the CUDA 13 build (it requires `cuda-toolkit==13.0.2` and the `-cu13` NVIDIA libraries; verified through the mirror's PEP 658 metadata). **Databricks laptops block public package indexes**: a managed `/etc/hosts` maps `pypi.org`, `download.pytorch.org`, `pypi.nvidia.com`, and other indexes to loopback, and Docker Desktop resolves container names through the host, so builds fail with `Connection refused`. Installs there go through the internal mirror `https://pypi-proxy.dev.databricks.com/simple` (set in `~/.config/pip/pip.conf` and `~/.config/uv/uv.toml`), which the container can't see — the push script passes it in. The build context is `train/`, and the Dockerfile copies only `requirements.txt` from it. Code is **not** baked in — `code_source` uploads `train/` per run (which includes `train/docker/`, harmlessly) — so rebuild only when `requirements.txt` changes.
- **Pushing the image** (`train/docker/build_and_push.sh`, following the Artifact Registry get-started guide): it reads its destination from `train.yaml`'s `environment.unity_catalog_image` — the single place the image name and tag live — resolves the build's package index (`--index-url`, then `$PIP_INDEX_URL`, then `index-url` from the user's pip config, else public PyPI; it refuses URLs with inline credentials because build args land in the immutable image history, and stops early with a hint when `/etc/hosts` blocks `pypi.org` and no mirror is set), checks the Software Artifacts API and stops before building if Artifact Registry isn't enabled in the workspace (a disabled preview otherwise surfaces only as a bare `403 Forbidden` on the first blob `HEAD` of the push), validates the image name against Artifact Registry's artifact-name rules (lowercase letters/digits/`_`/`-`, alphanumeric at both ends, at most two consecutive underscores, no underscore next to a hyphen, ≤255 chars) before building, builds with `--platform linux/amd64` (the base is amd64-only) and `--provenance=false --sbom=false` — **required**: with attestations, Docker Desktop's containerd image store saves an OCI image index (image + attestation manifest), and Artifact Registry fails that index upload with a bare `Internal Server Error` after every layer is up, registering no version (verified 2026-10-07; the attestation-free build has the identical image digest) — and pushes with `--platform linux/amd64` when a `--skip-build` local image is still an index, runs `databricks auth docker configure --profile <p>` (installs the `docker-credential-databricks` helper and saves the profile's `workspace_id`; needs a **workspace OAuth profile** — PAT/M2M profiles are unsupported), reads the registry host (`<workspace-id>.container.<region>.cloud.databricks.com`) from `databricks auth docker host`, then `docker tag`/`docker push`es `<host>/<catalog>.<schema>.<artifact>:<tag>` and lists versions via the Software Artifacts API. The script is bash 3.2-compatible (macOS's `/bin/bash`). Artifact Registry doesn't create the catalog/schema; pushing a new artifact needs `USE CATALOG` + `USE SCHEMA` + `CREATE VOLUME`, a new version or moved tag needs `WRITE VOLUME`, and running it needs `READ VOLUME`. Versions are immutable and cannot be deleted, so never bake credentials into the image.
- **Running the image** (per the AI Runtime custom-image docs): `train.yaml` references it as `environment.unity_catalog_image: <catalog>.<schema>.<artifact>:<tag>` — no registry hostname — and the CLI validates that format and rejects it alongside `environment.version`/`dependencies`. The image must be in Artifact Registry in the submitting workspace and under 20 GB; `WORKDIR` is ignored (use absolute paths like `$CODE_SOURCE_PATH/train.py`); running it needs Databricks CLI ≥ 1.19.0 (the push itself needs ≥ 1.18.0) and the **AI Runtime Beta Features** + **Databricks Artifact Registry** workspace previews. The custom-image docs do not list `MLFLOW_RUN_ID` or `HYPERPARAMETERS_PATH` among the injected variables, so `train.py` tolerates both being absent (it resolves the experiment itself, and `load_training_config()` falls back to the snapshot's `train.yaml`, losing only `--override` values).
- **opencv/FIPS is a resolution-time constraint, not a wall** (re-verified 2026-09-21). `opencv-python-headless>=4.13` still aborts vLLM at startup with `FATAL FIPS SELFTEST FAILURE` on Model Serving's FIPS pods, and the upstream bug (opencv/opencv-python#1191) is still open — so opencv must stay at `4.12.0.88`. But vLLM only needs opencv for video IO, so the standard internal workaround is to install a **modern vLLM first, then force `opencv-python-headless==4.12.0.88` in a SECOND install pass** and accept the conflict (plain `pip` prints a warning; the notebook's `%uv pip` does not check against installed packages, so it is silent — the pattern was field-validated with `pip`). Field-validated on Custom LLM Serving in July 2026 (Gemma 4 12B on `GPU_MEDIUM`) with `vllm==0.24.0` + `transformers==5.13.0` + `mlflow==3.14.0` — note `mlflow==3.12` is uninstallable next to vllm 0.24 (starlette conflict). A single `pip_requirements` list is resolved in one pass, so the conflicting pins **cannot** be expressed there; the working pattern installs both passes in the notebook and lets `env_pack` capture that environment (Databricks' own starter notebook passes only `extra_pip_requirements=["mlflow==3.12.0"]` and lets MLflow infer the rest). Trade-off to state to customers: opencv `<4.13` carries a known RCE CVE, which is why the managed Foundation Model path still treats this as blocked while per-model pins work.
- Qwen3.5 serving is what this repo now does, on the two-pass path above (internally it has also run on vLLM 0.17.0 for notebook evals and 0.18.0 for `Qwen/Qwen3.5-122B-A10B-FP8`). `--reasoning-parser qwen3` is the alternative if thinking ever has to stay on: it splits reasoning into `reasoning_content` so `content` stays clean JSON, at the cost of a much larger `max_tokens` budget.
- Databricks' current custom-LLM starter notebook (docs page updated 2026-09-11) pins `vllm==0.11.2`, `transformers==4.57.6`, `opencv-python-headless==4.12.*`, `mlflow==3.12.0`, `databricks-sdk>=0.102.0`, and **`flashinfer-cubin==0.5.2`** — those precompiled cubins are a cleaner fix for the missing `ninja`/`nvcc` than this repo's `VLLM_USE_FLASHINFER_SAMPLER=0`. Never pin `flashinfer-cubin` yourself: vLLM requires an exact version (0.11.2→0.5.2, 0.24.0→0.6.12), so a mismatched pin fails dependency resolution outright (`ResolutionImpossible` under pip); let vLLM pull it. and `env_pack` is required because custom LLM serving runs on [Serverless Optimized Deployments](https://docs.databricks.com/aws/en/machine-learning/model-serving/serverless-optimized-deployments). Supported workload types are `GPU_SMALL` (T4), `GPU_MEDIUM` (A10), `GPU_XLARGE` (H100).
- **Qwen3.5 has no non-thinking variant** — thinking is on by default, and an unsuppressed reasoning preamble truncates the JSON at `max_tokens`. Suppression must hold on both sides (see the prompt contract). This is also why `train.py` applies the chat template itself instead of letting TRL do it: that is the only way `enable_thinking=False` reaches the render. `Qwen3.5-4B` is natively multimodal (`Qwen3_5ForConditionalGeneration` + `vision_config`), but training loads the text backbone through `AutoModelForCausalLM` → `Qwen3_5ForCausalLM` (the documented text-only path) and serving passes `--language-model-only`. Training text-only is fine; **serving text-only is not** — the merge step re-wraps the fine-tuned backbone in the composite shape (next bullet).
- Qwen3.5's attention stack is **3:1 hybrid** — three Gated DeltaNet (linear attention) layers per Gated Attention layer, per the checkpoint's `layer_types`. LoRA therefore lands on `q/k/v/o_proj` only in the full-attention layers plus every layer's MLP projections; the DeltaNet `linear_attn.*` projections are deliberately unadapted. The DeltaNet path also wants the optional `causal_conv1d` and `fla` packages for its fast kernels — without them transformers silently falls back to slower, more memory-hungry PyTorch ops, so add them if training throughput matters (neither is installed here, to keep the env build simple).
- **vLLM 0.24.0 has no registry entry for `Qwen3_5ForCausalLM`**, so a text-only Qwen3.5 checkpoint cannot be served as-is (verified against the v0.24.0 source, 2026-09-21). The class *is* implemented (`vllm/model_executor/models/qwen3_5.py:539`) but is absent from `registry.py`'s dict, which lists only `Qwen3_5ForConditionalGeneration`/`Qwen3_5MoeForConditionalGeneration`/`Qwen3_5MTP`. `_normalize_arch()` (`registry.py:1148`) then rewrites the `ForCausalLM` suffix until a registered name matches, and `inspect_model_cls()` returns the *original* name for logging — so the log reads `Resolved architecture: Qwen3_5ForCausalLM` while the multimodal class is what gets built, dying on `config.vision_config` with `AttributeError: 'Qwen3_5TextConfig' object has no attribute 'vision_config'`. Three workarounds are dead ends: `--language-model-only` only zeroes the modality limits and toggles a fused qwen3-next kernel (it never selects the text class); patching `vision_config` in via `--hf-overrides` leaves the tower's parameters uninitialized and `default_loader.py:466` **raises** on those; and `--model-impl transformers` has no hybrid/Mamba support, so it cannot allocate Qwen3.5's Gated DeltaNet state. The fix is in the merge step — save the composite shape, vision weights included, carried over from the base checkpoint (`merge_adapter_to_serving_checkpoint()` in `train.py`). The idle tower costs ~1 GB of weights. The upstream fix is a one-line registry addition and worth reporting.
- Custom LLM serving beta does not support scale-to-zero with `GPU_XLARGE` — the deploy cell raises if both are set.
- Capacity is **fixed** during beta (no autoscaling between replicas): `serving_workload_size` sets the replica count and requests beyond provisioned capacity are rejected with instant 429s (the threshold is not user-configurable). Measured on this workload: one `GPU_MEDIUM` (A10) replica sustains ~150 successful QPS at ~1.1-1.4s latency with `max_tokens: 64-128`. Size for peak: 10K QPS needs `Large` + `GPU_XLARGE`-class capacity or multiple endpoints sharded client-side. The load generator itself caps out at (cluster task slots) × (per-worker rate) — `load_generator_workers` must not exceed available Spark task slots or achieved QPS silently falls short with zero 429s.
- The serving container has no `ninja`/`nvcc`, so FlashInfer (present in the Databricks AI base env) cannot JIT-compile kernels — vLLM crashes at sampler warmup with `FileNotFoundError: 'ninja'` unless the served entity sets `VLLM_USE_FLASHINFER_SAMPLER=0` (done via `environment_vars` in the deploy cell; this is runtime config, no re-registration needed).
- **Training stack contract** (`train/train.py`): assistant-only loss comes from TRL's prompt-completion dataset format — each row is mapped to a conversational `prompt` (user turn) plus `completion` (assistant turn) and `completion_only_loss=True` masks the prompt, replacing hand-written response markers. `SFTConfig` takes `max_length` (TRL renamed `max_seq_length` in 0.20), and `LoraConfig` is passed to `SFTTrainer` as `peft_config` rather than pre-wrapping the model: TRL applies the adapter and calls `enable_input_require_grads()` so gradient checkpointing yields adapter gradients, and it rejects an already-PEFT-wrapped model when `peft_config` is set. The optimizer is `adamw_torch_fused`, not the old `adamw_8bit`: v6 dropped `bitsandbytes` from the base image. Per-step metrics reach MLflow through `MLflowStepMetricsCallback`, not `report_to="mlflow"` — HF's built-in callback also re-logs every `TrainingArguments` field as a param and owns the run lifecycle, which collides with the run `train_qwen3_sft()` opens. The callback forwards **whatever the trainer emits** rather than a hardcoded list (`loss`, `mean_token_accuracy`, `grad_norm`, `learning_rate`, `entropy`, `num_tokens`, `epoch`, plus `aux_loss` on MoE), so a TRL version that renames or adds a metric needs no change here, and adds `tokens_per_second` plus CUDA memory. It logs only on `state.is_world_process_zero` (the other ranks have no run open) and swallows tracking-server errors with a one-time warning so telemetry can never fail a training run. `logging_steps=1` is what makes it per-step; raise it for long runs.
- The CLI `command` must start **one process per GPU** (`torchrun --nproc_per_node=gpu`): a single process holding every GPU makes HF Trainer fall back to `nn.DataParallel`, which crashes Qwen3.5's Gated DeltaNet path ("lazy wrapper should be called at most once") and reads only rank 0's shard slice (`_warn_single_process_multi_gpu()` in `train.py` flags it).
- Multi-GPU DDP needs **non-reentrant** gradient checkpointing (`gradient_checkpointing_kwargs={"use_reentrant": False}` in `SFTConfig`): the reentrant implementation fires each LoRA parameter's gradient hook twice and dies with "Expected to mark a variable ready only once". `ddp_find_unused_parameters=False` is set explicitly — every LoRA parameter gets a gradient each step, and the unused-parameter scan conflicts with checkpointing.
- Both launchers log to the experiment named by `train.yaml`'s top-level `experiment_name` inside its `mlflow_experiment_directory`; no experiment path belongs in code or the notebook. `load_training_config()` binds them as `EXPERIMENT_NAME`/`EXPERIMENT_DIRECTORY` (`None` when the directory is unset), and `resolve_experiment_path(name, directory)` mirrors AIR: it creates the directory if missing (as the CLI does before submitting — `mlflow.set_experiment()` fails on a missing parent), strips the `/Workspace` prefix (MLflow names workspace experiments without it), falls back to `/Users/<current user>` when no directory is set (via `WorkspaceClient`, so it needs no Spark session), and passes through a name that already starts with `/`. The runner notebook calls it once (`MLFLOW_EXPERIMENT_PATH`), sets it on the driver, and forwards it into `run_rank_training(experiment_path=...)` so the rank-0 GPU worker logs there instead of relying on the launcher to propagate the driver's active experiment. `main()` passes `None` when `MLFLOW_RUN_ID` is set — AIR already created the workload run in that experiment and exported its id, which rank 0's `mlflow.start_run()` resumes — and otherwise (a bare `python train.py`, or a custom image that doesn't inject it) resolves the experiment itself on rank 0 only. AIR also records system metrics for CLI runs, so `train.py` only enables MLflow's in-process `log_system_metrics` on the notebook path. `train.yaml` sets `max_retries: 0` — the CLI default is 3, and each retry would be a fresh workload and a new MLflow run in the same experiment.
